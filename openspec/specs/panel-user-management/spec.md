# Panel User Management Specification

## Purpose
The implementer (P1) creates and manages the client administrators (P2) who log into the panel (story **T3**), from the console. Decisions: DEC-155 to DEC-158. Every route requires an operator session (DEC-152) and is tenant-scoped by `X-Tenant-Id` (DEC-15); the panel never calls them.

## Requirements

### Requirement: Generated Password
A panel user's password SHALL be generated by the system from at least 18 random bytes encoded as base64url, and only its `scrypt` hash (DEC-133) SHALL be stored. A generated password SHALL appear only in the response of the request that generated it, with `Cache-Control: no-store`; it SHALL NOT appear in any other response, in an error body, or in a log line.

#### Scenario: Two generated passwords differ and are stored hashed
- **WHEN** two users are created
- **THEN** their passwords differ, each is at least 24 characters, and neither equals its stored `claveHash`

### Requirement: Create a Panel User
`POST /usuarios` SHALL accept a strict JSON body `{ correo, nombre? }` with no other key. `correo` SHALL be trimmed and lowercased, 3 to 254 characters, with one `@` that is neither the first nor the last character; `nombre`, when present, SHALL be trimmed, 1 to 120 characters, and blank SHALL be stored as null. The user SHALL be created active in the header's tenant and the answer SHALL be 201 `{ usuario: { id, correo, nombre, activo, creadoEn }, clave }`. A `correo` that already exists in any tenant SHALL be 409 `correo-en-uso`, the same answer whichever tenant holds it. A malformed body SHALL be 400 `solicitud-invalida` with `campos`.

#### Scenario: Create
- **GIVEN** tenant A
- **WHEN** `POST /usuarios` sends `{ "correo": " Ana@Negocio.com ", "nombre": "Ana" }`
- **THEN** the answer is 201 with `correo` "ana@negocio.com", `activo` true and a `clave`, and that password logs into the panel

#### Scenario: Email taken in another tenant
- **GIVEN** "ana@negocio.com" exists in tenant B
- **WHEN** tenant A creates "ANA@negocio.com"
- **THEN** the answer is 409 `correo-en-uso`, nothing is created, and the body names no tenant

#### Scenario: Strict body
- **WHEN** the body adds `tenantId` or `clave`, or the `correo` has no `@`
- **THEN** the answer is 400 `solicitud-invalida` and nothing is created

### Requirement: List Panel Users
`GET /usuarios` SHALL answer the header tenant's users, ordered by `correo`, each with `id`, `correo`, `nombre`, `activo` and `creadoEn` only, capped by `LIMITE_LISTADO` with `truncado`.

#### Scenario: Only the tenant's users, never a hash
- **GIVEN** users in tenants A and B
- **WHEN** tenant A lists
- **THEN** only A's users appear, and no entry has `claveHash` or `tenantId`

### Requirement: Reset a Password
`POST /usuarios/:id/clave` SHALL generate a new password, replace the hash, delete every session of that user in the same transaction, and answer 200 `{ usuario, clave }` with `Cache-Control: no-store`. It SHALL work for an inactive user too, which stays inactive.

#### Scenario: Reset revokes and replaces
- **GIVEN** a user with an open panel session
- **WHEN** the operator resets the password
- **THEN** the old password and the old session are refused, and the new password logs in

### Requirement: Deactivate and Reactivate
`POST /usuarios/:id/desactivar` SHALL set `activo` false and delete every session of the user in the same transaction, answering 200 `{ usuario }`; an already inactive user SHALL be 409 `usuario-inactivo`. `POST /usuarios/:id/reactivar` SHALL set `activo` true without touching the password, answering 200 `{ usuario }`; an active user SHALL be 409 `usuario-activo`. No route SHALL delete a user.

#### Scenario: Deactivate cuts access, reactivate restores it
- **GIVEN** a user with an open panel session
- **WHEN** the operator deactivates it
- **THEN** the session row no longer exists, the cookie is refused and a login with the same password is refused
- **WHEN** the operator reactivates it
- **THEN** the same password logs in again

### Requirement: Tenant Isolation of User Routes
Every route SHALL resolve `:id` through the tenant-scoped client: an id of another tenant SHALL answer 404 `usuario-no-encontrado`, exactly like an unknown id, and SHALL change nothing in the other tenant.

#### Scenario: Tenant A cannot touch tenant B's user
- **GIVEN** a user of tenant B
- **WHEN** tenant A calls reset, deactivate or reactivate with its id
- **THEN** each answer is 404 `usuario-no-encontrado` and the user, its hash and its sessions are unchanged

### Requirement: Smoke Creates a Panel User
`scripts/smoke.sh` SHALL create a panel user from the console, log into the panel with the generated password, and deactivate it, checking that the panel login is refused afterwards.
