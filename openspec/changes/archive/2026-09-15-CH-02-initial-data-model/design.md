# Design: CH-02 — Initial Data Model

## Inputs

- `proposal.md` (this change)
- `specs/domain-data-model/spec.md` (this change) — 4 requirements this design satisfies
- `docs/01-decisiones.md`, DEC-06 — minimal `tenant` now, not deferred to CH-06
- `docs/00-contexto.md` §8 — the eight named domain entities
- CH-01's `prisma/schema.prisma` (datasource/generator only, Prisma 7 with `@prisma/adapter-pg`)

## Naming: Spanish model and field names

**Decision.** Prisma model names match the Spanish nouns already used as the ubiquitous language across every project document: `Tenant`, `Conexion`, `ConsultaGuardada` (PascalCase, Prisma convention). Fields use Spanish where the domain vocabulary already names them (`nombre`, `descripcion`, `credencial`), English where Prisma/TypeScript idiom already fixes the term (`id`, standard timestamp suffixes).

**Alternatives considered:** fully English model/field names (`Connection`, `SavedQuery`) — rejected because it would create a second vocabulary the docs and code would need translating between, undermining the traceability `AGENTS.md` asks for between spec and implementation.

**Resigned:** mixed-language identifiers read awkwardly to a reader expecting one convention throughout; accepted because the alternative (translating the domain) is worse for this project's specific goal of thesis traceability.

## No `@map`/`@@map`

**Decision.** No explicit `@map`/`@@map` directives. Prisma's default camelCase-in-schema, and its default table/column naming, are used as-is.

**Why.** Nothing in this change reads these tables outside Prisma; CH-01 established Prisma as the only path to the own database (migrations-only rule). Introducing a raw-SQL/ORM naming split now would be speculative.

## Schema

```prisma
model Tenant {
  id                 String             @id @default(uuid())
  nombre             String
  creadoEn           DateTime           @default(now())
  conexiones         Conexion[]
  consultasGuardadas ConsultaGuardada[]
}

model Conexion {
  id            String   @id @default(uuid())
  tenantId      String
  tenant        Tenant   @relation(fields: [tenantId], references: [id])
  nombre        String
  motor         String
  host          String
  puerto        Int
  baseDeDatos   String
  usuarioDb     String
  credencial    String
  soloLectura   Boolean  @default(true)
  creadaEn      DateTime @default(now())
  actualizadaEn DateTime @updatedAt

  @@index([tenantId])
}

model ConsultaGuardada {
  id            String   @id @default(uuid())
  tenantId      String
  tenant        Tenant   @relation(fields: [tenantId], references: [id])
  nombre        String
  descripcion   String?
  sql           String
  creadaEn      DateTime @default(now())
  actualizadaEn DateTime @updatedAt

  @@index([tenantId])
}
```

### Field notes

- `Tenant.nombre` — required. R0 seeds one row (working name: `"Food Store"`, matching `docs/02-mapa-de-changes.md`'s own closure test — connecting to "la base de Food Store"). No `activo`/soft-delete field: that belongs to story T1 (CH-06), which this change does not implement.
- `Conexion.motor` — plain `String`, not an enum. D-4 (`docs/01-decisiones.md`) — which engines are admitted for a client's replica — is an open gate; an enum here would resolve it by accident.
- `Conexion.usuarioDb` — named to avoid collision with the future `Usuario` (application user / story T3) entity; this is the *database* username the connection authenticates as, unrelated to any application login.
- `Conexion.credencial` — plain `String`. **Not encrypted.** Story A2 (credentials encrypted at rest, key outside the database) is R1. Whatever change first writes a real credential into this column (CH-03) inherits that gap; this design does not claim encryption anywhere in naming or comments, so the gap stays visible rather than implied-away.
- `Conexion.soloLectura` — defaults `true`. Recorded per-connection because story A3 already frames read-only as enforced "en dos capas" (application + database user); this column is the application-layer record of that second-layer expectation, not the enforcement itself (enforcement is CH-04's job, story A3).
- `ConsultaGuardada.descripcion` — optional (`String?`), per story B2's own wording ("nombre y descripción") and the spec scenario allowing it empty.
- `ConsultaGuardada.sql` — raw text of the saved query. No parameter/placeholder structure yet — that is story B3 (parametrization), R1.
- `@@index([tenantId])` on both child tables — every realistic query pattern from CH-03 onward (A1: list connections; B2: list saved queries) filters by tenant first; added now since it costs nothing and avoids a later migration purely to add an index CH-06 will need immediately for T2's isolation tests.

## Migration and seed

- One Prisma migration, generated by `prisma migrate dev` at implementation time, creating all three tables plus the two foreign keys and the two indexes above.
- The seed inserts exactly one `Tenant` row. Per CH-01's design, `prisma migrate deploy` runs from the Docker entrypoint on every bring-up; the seed step SHALL run only when the `Tenant` table is empty (idempotent — matches CH-01's existing idempotency requirement for the migration step, spec scenario "Re-running migrations").
- No seed data for `Conexion` or `ConsultaGuardada` — those are populated by CH-03 and CH-05 respectively, not by this change.

**Amended during apply — seed script import path.** `prisma/seed.ts` runs via `npx tsx prisma/seed.ts` (not compiled by `tsc`: `tsconfig.json`'s `include` is `["src"]` only, and `prisma/` sits outside it). The generated Prisma client under `src/generated/prisma` only exists in the build stage of CH-01's Dockerfile — the runtime image copies `dist/` and `prisma/`, not `src/`. Importing `../src/generated/prisma/client.js` from the seed script therefore resolves inside the build stage but throws `ERR_MODULE_NOT_FOUND` in the runtime container (caught during this change's Docker verification). Fixed by importing `../dist/generated/prisma/client.js` instead — `tsc` compiles `src/generated/prisma/*.ts` into `dist/generated/prisma/*.js` as part of the normal build (same mechanism CH-01's `dist/health.js` already relies on for its own relative import), and `dist/` is present in both the runtime image and any local run that already built once. Consequence: `npm run seed` locally requires `npm run build` to have run first — consistent with `npm start`'s existing requirement, not a new constraint class.

## Migration generation environment note (found during apply, not a design decision)

Generating the migration with `prisma migrate dev` needs a schema-diffing connection to a reachable Postgres. Two dead ends before the working path, kept here so a future change doesn't repeat them:

- `docker compose run --rm app npx prisma migrate dev ...` applies the migration correctly, but `--rm` removes the container on exit — the generated `prisma/migrations/*/migration.sql` only ever existed in that container's writable layer and was lost with it.
- `docker compose run --rm -v "$(pwd)/prisma:/app/prisma" app ...` (bind-mounting the host `prisma/` directory into the same command) did not actually bind to the host under this Windows/Git-Bash/Docker Desktop combination — writes from inside the container did not appear on the host, with no error raised.

**What worked:** run `prisma migrate dev` directly on the Windows host (Node.js and `node_modules` already present there from CH-01), against the `db` container's Postgres reached through a *temporary* `ports: ["5432:5432"]` line added to `docker-compose.yml`'s `db` service, then removed immediately after the migration file was generated. The generated `prisma/migrations/` folder is a normal source artifact from that point on — every later bring-up (Docker or host) uses `prisma migrate deploy`, which needs no shadow database and no port exposure.

## Scope check against the 4 requirements

| Requirement (spec.md) | Covered by |
|---|---|
| Tenant Table With a Single Seeded Row | `Tenant` model + idempotent seed step |
| Connection Records Scoped to a Tenant | `Conexion.tenantId` required FK |
| Saved Query Records Scoped to a Tenant | `ConsultaGuardada.tenantId` required FK |
| No Premature Modeling of Out-of-Release Entities | Schema contains only the three models above |

## Out of scope (unchanged from proposal.md)

No tenant lifecycle/isolation, no credential encryption, no execution log, no `usuario`, no `plantilla`/`automatizacion`/`mapeo`. Those start at CH-03, A2/CH-0x, CH-13, T3/CH-22, and R1's block D/M respectively.
